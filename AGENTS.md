# goskills

Репозиторий переиспользуемых навыков OpenCode для Go-проектов. Это не
Go-модуль: здесь нет `go.mod`, `Makefile` и бинарей. Содержимое — Markdown,
YAML frontmatter и эталонные файлы в `references/`.

## Иерархия правил

- Глобальные правила — `~/.config/opencode/AGENTS.md`.
- Правила этого репозитория — этот файл; при конфликте он важнее.
- Универсальные методологии — в `skills/*`; здесь только факты и решения
  репозитория, без дублирования текста навыков.

## Структура

```schema
.
├── skills/
│   └── <skill-id>/
│       ├── SKILL.md
│       └── references/
├── docs/
│   ├── specs/        # факты о системе
│   └── drafts/       # черновики, не инструкции
├── README.md         # подключение навыков
├── CHANGELOG.md      # одна строка на изменение
└── .agentignore
```

- `skills/<id>/SKILL.md` — один навык = один вопрос.
- `references/` — готовые файлы для копирования в проект (`Makefile`,
  `.gitignore`, `.agentignore`, шаблон `AGENTS.md`).
- `docs/specs/` — спецификации-факты; индекс ведётся в
  `docs/specs/README.md`.
- `docs/drafts/` — черновики для книги; не источник истины и не инструкции.
  Нумерация `NNNN-kebab-case.md` сквозная и не меняется.

## Навыки

| Навык | Когда использовать |
|---|---|
| `bootstrap` | создание Go-проекта с нуля |
| `project-structure` | где лежит файл, раскладка каталогов |
| `architecture` | зависимости и границы слоёв |
| `services` | каталог на сервис, use cases, DTO, оркестрация и саги |
| `config` | источники, композиция и валидация конфига |
| `testing` | unit, интеграционные и e2e-тесты |
| `makefile` | цели, `.bin-deps`, workspace-Makefile |
| `gitignore` | что не коммитить |
| `agentignore` | что агент не читает; OpenCode — `permissions` |
| `agents-md` | проектная память и каркас `AGENTS.md` |
| `skill-creator` | создание и правка навыков |
| `commit-conventions` | формат коммитов |
| `changelog` | ведение `CHANGELOG.md` |
| `prompt-engineering` | промпты и prompt-cache |

Навыки подключаются через `opencode.jsonc` (см. README). Перед работой
проверить, подходит ли задача под описание навыка; если да — загрузить его.

## Workflow

1. Уточнить задачу и найти релевантный навык.
2. Менять один источник истины: навык, `references/` или документ.
3. Новый навык — по `skills/skill-creator`.
4. Проверить YAML frontmatter и отсутствие дублей.
5. Обновить `CHANGELOG.md`: дата, область, краткое изменение, автор.
6. Коммит — только по запросу пользователя, по `commit-conventions`.
7. Вывести итог: что изменено и какие проверки пройдены.

## Проверки

```bash
# frontmatter всех навыков парсится и содержит name/description
for f in skills/*/SKILL.md; do
  ruby -ryaml -e 'd=YAML.load_file(ARGV[0]); abort unless d["name"] && d["description"]' "$f"
done

# нет конфликтных маркеров и лишних пробелов
git diff --check
```

`make`-целей в репозитории нет; не выдумывать `make build` и подобные.

## Спеки и навыки

| | Спека | Навык |
|---|---|---|
| Отвечает на вопрос | **что** устроено | **как** делать |
| Содержит | факты, схемы, контракты | процесс, шаги, чек-лист |
| Где лежит | `docs/specs/` | `skills/*` |
| Как читать | 1–2 релевантных, не все | по триггеру из описания |

Спеки — источник истины о системе. Не загружать все сразу. Черновики в
`docs/drafts/` не являются инструкциями для агента.

## Правила репозитория

- Один навык — один вопрос; не дублировать правила другого навыка, ссылаться
  по id (`skills/project-structure`).
- `description` во frontmatter всегда в двойных кавычках: двоеточие с
  пробелом ломает YAML.
- Пути в навыках — относительно навыка: `references/Makefile`.
- Эталонные файлы в `references/` должны быть готовы к копированию в корень
  проекта.
- README и CHANGELOG обновляются в том же изменении.
- Не добавлять в репозиторий секреты, реальные `.env` и токены.
- Текст — для человека и агента: простые формулировки, расшифровка
  терминов, примеры. Без машинного жаргона и «телеграфного» стиля: этот
  репозиторий читают и разработчики, и агенты.

## Ключевые решения

- Конфиг один на модуль: `internal/config`, без деления по приложениям;
  локальные `Config` — в адаптерах, валидация в `New`.
- `internal/app/<appname>/app.go` — DI приложения; `cmd` — только bootstrap,
  сигналы ОС и запуск/останов.
- Сервисы — каталог на сервис: `services/<appname>/<service>/` с `ports.go`,
  `service.go`, `dto.go` и файлом на операцию (`register.go`, `unregister.go`).
- `Makefile` один на модуль/workspace, цели с именем приложения:
  `build-<app>`, `run-<app>`; версия Go только в `go.mod`.
- Тестовый стек по умолчанию — `mockery` + `testify`; моки генерируются.
- `.agentignore` не читается OpenCode; для него правила переносятся в
  `permissions` с `action: "read"`.
- Короткое имя модуля допустимо только для неимпортируемого проекта, причина
  фиксируется в `AGENTS.md`/README проекта.

## Безопасность

- `.agentignore` — не граница безопасности: shell-команды его обходят.
- Секреты не хранятся в репозитории; только env/Secret.
- `.env` и локальные конфиги не коммитятся; правила — `skills/gitignore`.
- Для OpenCode доступ к секретам закрывается `permissions`, пример — в README.
