# Структура Go-проекта

Навык отвечает на вопрос «**где лежит файл**» и «**как инициализировать проект**».
Вопрос «**что может импортировать**» — в `skills/architecture`.

## Инициализация проекта

Выполняется, если в корне проекта отсутствует `go.mod`. Если `go.mod` есть —
раздел пропускается, проект считается инициализированным.

### Шаг 1. Определить имя модуля

Правила по приоритету:

1. Если есть git remote — взять путь из него.
   Пример: `git@github.com:org/repo.git` → `github.com/org/repo`.
2. Если git remote нет, но есть `go.work` или родительский `go.mod` —
   использовать их как источник имени (для вложенных модулей).
3. Иначе — **спросить пользователя**. Не угадывать по имени каталога,
   не использовать `example.com/...` по умолчанию.

Запрещено:
- Угадывать имя модуля по имени локального каталога.
- Использовать заглушку вроде `example.com/project` без явного согласия.

### Шаг 2. Определить версию Go

- Минимальная поддерживаемая версия: `1.26`.
- Если пользователь явно указал другую версию — использовать её.
- Если в проекте уже есть `.go-version`, `toolchain` или CI-конфиг
  с версией Go — взять версию оттуда, не переопределять.

### Шаг 3. Выполнить инициализацию

```bash
go mod init <module>
```

Проверка: go.mod создан, содержит корректные module и go.

### Шаг 4. Перейти к структуре

После успешного go mod init — перейти к разделу «Структура каталогов»
этого же навыка. Не создавать каталоги до инициализации модуля.

Что не делать:
- Не добавлять зависимости в go.mod на этом шаге — только module и go.
- Не создавать main.go или другие файлы до определения структуры.
- Не выполнять go mod tidy на пустом модуле — нечего tidy.

## Структура каталогов

Базовая раскладка:

```schema
.
├── go.mod
├── Dockerfile
├── Makefile
├── README.md
├── .gitignore
├── api/
├── bin/
├── config/
│   └── .env.example
├── cmd/
│   └── appname/
│       └── main.go
├── internal/
│   ├── app/
│   │   └── appname/
│   │       └── app.go
│   ├── config/
|   │   └── appname/
│   │       └── config.go
│   ├── domain/
│   ├── infra/
│   │   ├── http/
│   │   ├── grpc/
│   │   ├── kafka/
│   │   └── minio/
│   ├── platform/
│   │   ├── config/
│   │   ├── logger
│   │   └── tracing/
│   ├── repository/
│   ├── services/
│   ├── shared/
│   └── transport/
│       └── appname/
│           ├── http/
│           ├── grpc/
│           ├── kafka/
│           └── websocket/
└── tests/
```

## Назначение каталогов (черновик!!!)

- cmd/<app-name>/main.go — точка сборки. Единственное место, где видно, какие адаптеры включены в данный срез. Здесь создаются конкретные реализации и передаются в core.
- internal/ — домен и порты. Не зависит от адаптеров и внешних библиотек.
- internal/domain/ — типы, сущности, бизнес-правила.
- core/ports/ — интерфейсы, которые реализуют адаптеры.
- adapters/ — реализации портов: HTTP, gRPC, Kafka, MinIO и т.д.
- Каждый адаптер — отдельный подкаталог, самодостаточный.
- internal/ — код, который не должен импортироваться извне модуля. Используется, если проект — библиотека или имеет внешних потребителей.

## Куда класть новый файл (черновик!!!)

| Что создаётся | Куда класть|
|---|---|
| Новая сущность домена | internal/domain/<entity-name>/ |
| Новый интерфейс (порт) | core/ports/ |
| Реализация внешнего сервиса (Kafka, MinIO, HTTP, gRPC) | internal/infra/<adapter-name>/ |
| Точка сборки, wiring | cmd/app/main.go |
| Вспомогательный код, не для внешнего использования | internal/ |
| Код, предназначенный для внешних потребителей | pkg/ (только если правда нужно) |

## Что не создавать
- Пустые каталоги «на будущее» — создаются при появлении первого файла.
- pkg/ без реальной необходимости — по умолчанию его нет.
- util/, common/, helpers/ — это свалка; код кладётся туда, где он используется, или в домен.
- Дублирующие пакеты в internal/ и core/ одновременно.
