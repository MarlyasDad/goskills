# Создание навыка

Навык отвечает на вопрос «**как оформить новый skill**». Содержание
конкретных навыков — в их собственных `SKILL.md`.

## Каталог

```schema
skills/
└── <skill-id>/
    ├── SKILL.md
    └── references/
        └── <файл-эталон или проверка>
```

- `<skill-id>` — латиница в нижнем регистре, слова через `-`:
  `project-structure`, `agents-md`, `skill-creator`.
- `name` во frontmatter совпадает с `<skill-id>`.
- В `references/` лежат готовые файлы для проекта (`Makefile`, `.gitignore`,
  `.agentignore`, шаблон `AGENTS.md`) и небольшие проверки на Go, например
  `check_frontmatter.go`.
- Пути в тексте — относительно навыка: `references/Makefile`.

## Frontmatter

```yaml
---
name: <skill-id>
description: "<что делает, когда применяется и чего не описывает>"
license: MIT
compatibility: opencode
metadata:
  audience: developer
  workflow: <scaffolding|architecture|configuration|testing|tooling|documentation>
---
```

Правила YAML:

- **`description` всегда в двойных кавычках.** Двоеточие с пробелом (`: `)
  внутри незакавыченного значения ломает YAML:
  `mapping values are not allowed in this context`.
- Нужно двоеточие в значении — оберни всё значение в двойные кавычки:
  `description: "Правила проекта: структура и конфиг"`. Правило относится к
  любому полю frontmatter, а не только к `description`.
- Кавычки внутри значения экранируются: `\"`.
- Если значение начинается с `*`, `&`, `!`, `-`, `{`, `[`, `#`, `>` или
  содержит ` #`, его тоже нужно цитировать.
- Перед коммитом проверять frontmatter программой, а не глазами:
  `references/check_frontmatter.go` ловит типичные поломки YAML и нарушения
  схемы.

Пример ошибки:

```yaml
# плохо: двоеточие после «проекта» превращает строку в mapping
description: Правила проекта: структура и конфиг
```

```yaml
# хорошо
description: "Правила проекта: структура и конфиг"
```

## Описание

- Что навык делает и **когда** его загружать.
- Границы: что им не покрывается и в каком навыке это лежит.
- Без общих слов вроде «полезный навык». Агент выбирает навык по описанию.
- Одно-два предложения, конкретные триггеры: «при создании Makefile»,
  «при добавлении адаптера», «при обновлении AGENTS.md».

## Тело навыка

1. Заголовок `# <Название>`.
2. Назначение и границы с другими навыками.
3. Правила и порядок действий.
4. Примеры на Go или ссылка на `references/`.
5. Проверка/чек-лист.
6. Границы: «это здесь, а это — в другом навыке».

Пиши для человека и агента: короткие абзацы, расшифровка терминов, примеры.
Агент читает тот же текст, что и разработчик; «телеграфный» стиль и
машинный жаргон здесь не экономят, а запутывают.

Не дублировать другой навык: ссылаться на него по id
(`skills/project-structure`). Один вопрос — один навык.

Если это **факт** о системе (схема, контракт, статус) — это спека или
`AGENTS.md`, а не навык. Навык описывает повторяемый процесс «как делать».

## Язык и стиль

**Правило: всё в навыках — в едином стиле и на языке, про который
репозиторий.** Репозиторий про Go, поэтому примеры кода — на Go.
Объяснения по-русски, имена — из Go-проекта, команды — обычный shell.

- Примеры прикладного кода — только на Go и в стиле проекта: `gofmt`,
  `context`, ошибки через `error`, интерфейсы у потребителя.
- Команды — обычный shell, конфиги — YAML/JSON, если этого требует
  инструмент. Примеры на Ruby, Python или JavaScript не добавляются даже
  «для сравнения»: агент копирует стиль из примеров, а не из пояснений.
- Идентификаторы в коде и каталогах — английские (`domain`, `services`,
  `app.go`), объяснения — по-русски. Один и тот же слой называется
  одинаково во всех навыках.
- Новый навык не вводит свой словарь и свои команды для того, что уже
  описано: сверяйся с `skills/project-structure`, `skills/architecture` и
  `skills/makefile`.
- Если без внешнего инструмента не обойтись, назови его явно и оставь на
  краю примера, а не в центре процесса.

## Проверка

```bash
# из корня репозитория
# frontmatter: name совпадает с каталогом, description в кавычках
go run skills/skill-creator/references/check_frontmatter.go skills/*/SKILL.md

# нет конфликтных маркеров и лишних пробелов
git diff --check
```

Чек-лист:

- [ ] Каталог и `name` совпадают.
- [ ] `description` в кавычках и без сломанного YAML.
- [ ] Есть назначение, правила, проверка и границы.
- [ ] `references/` содержит эталонные файлы и проверки, а не копии чужих
      навыков.
- [ ] Нет дублей правил из других навыков.
- [ ] Примеры кода — на Go, команды — shell; вставок на других языках нет.
- [ ] Названия слоёв, каталогов и команд совпадают с другими навыками.
- [ ] README и CHANGELOG обновлены.
