# .dockerignore Go-проекта

Навык отвечает на вопрос «**что не должно попасть в контекст сборки Docker**».
Вопрос «что не коммитить» — `skills/gitignore`; «что не читает агент» —
`skills/agentignore`; где лежит `Dockerfile` — `skills/project-structure`.

## Зачем

- `docker build` отправляет демону весь build context, а `COPY . .` копирует
  из него всё, что не исключено.
- Большой контекст замедляет сборку. Если Dockerfile делает `COPY . .`,
  `.git`, `.env` и локальные конфиги могут попасть в слои образа, даже если
  финальный образ их потом не использует.
- `.dockerignore` — **не граница безопасности**: секреты не должны лежать в
  репозитории и передаваться через `ARG`/`ENV`.

## Файл

- Имя — `.dockerignore`, лежит в корне контекста сборки, рядом с
  `Dockerfile`.
- Если `Dockerfile` в подкаталоге, `.dockerignore` всё равно кладётся в корень
  контекста, а не обязательно рядом с `Dockerfile`.
- BuildKit также читает `<Dockerfile>.dockerignore` рядом с конкретным
  Dockerfile, если наборы для сборок должны различаться.
- По умолчанию один файл на контекст. Другой контекст — другой
  `.dockerignore`.
- Формат как у `.gitignore`: `*`, `?`, `**`, `!`, комментарии `#`.
- `!` возвращает файл в контекст, но не работает, если исключён его
  родительский каталог.
- Коммитится вместе с проектом.

## Что исключать

| Категория | Примеры |
|---|---|
| Git и CI | `.git/`, `.github/`, `.gitignore`, `.gitattributes` |
| Docker и локальная инфраструктура | `Dockerfile`, `.dockerignore`, `docker-compose*.yml` |
| Секреты и локальные конфиги | `.env`, `.env.*`, `configs/.env.*` |
| Сборка | `bin/`, `dist/`, `build/`, `out/`, `*.exe`, `*.so`, `*.dll` |
| Тесты и покрытие | `*.test`, `*.out`, `coverage.*`, `*.coverprofile` |
| Логи и временные файлы | `*.log`, `logs/`, `tmp/`, `.cache/` |
| IDE и ОС | `.idea/`, `.vscode/`, `.DS_Store`, `Thumbs.db`, `*.swp` |
| Артефакты ИИ-инструментов | `.agentignore`, `.claude/`, `.cursor/`, `.aider*` |

Шаблоны конфигов без секретов (`configs/.env.example`) можно оставить в
контексте отрицанием `!configs/.env.example`. Если приложение их не читает
при старте, проще исключить и их.

Не исключать:

- исходный код, `go.mod`, `go.sum`;
- `vendor/`, если проект собирается с вендором;
- `api/`, `migrations/`, `docs/`, `configs/`, если они нужны `go:embed` или
  приложению при запуске;
- `testdata/`, если он нужен тестам в стадии сборки.

## COPY . .

- Лучше копировать явно: `COPY go.mod go.sum ./`, затем нужные каталоги.
- `COPY . .` допустим только вместе с `.dockerignore`: иначе в образ
  попадут `.git`, локальные `.env` и артефакты.
- Multi-stage не спасает контекст: builder всё равно получает всё, что не
  исключено. В финальную стадию копируется только бинарь и нужные файлы.

## Секреты

- Реальные секреты — через BuildKit `--secret`, а не `ARG`/`ENV`.
- Не копировать `.env*` в образ и не печатать их в `RUN`.
- `.dockerignore` не очищает git-историю: если секрет уже закоммичен, его
  нужно отозвать, а не только исключить из контекста.

## Проверка

1. Собрать с подробным выводом и посмотреть размер контекста:

   ```bash
   docker build --progress=plain -t <app> .
   ```

   Строка `transferring context` показывает, сколько ушло демону. Если
   контекст неожиданно большой — искать забытый каталог.

2. Если база тянется из закрытого registry и сборка недоступна, проверь
   правила глазами и зафиксируй, что образ не собирался. Это не одно и то
   же: «контекст проверен» и «образ собран».
3. Для стадии с `COPY . .` можно проверить содержимое:

   ```bash
   docker run --rm <image> ls -la /app
   ```

4. Слои и лишние файлы — `dive <image>`, если инструмент есть.
5. `git check-ignore` здесь не работает: у `.dockerignore` свой синтаксис и
   свои правила.

## Порядок

1. Скопировать `references/.dockerignore` в корень контекста.
2. Добавить артефакты конкретного проекта (generated, dumps, локальные БД).
3. Проверить, что шаблон конфига не исключён, если он нужен:

   ```text
   configs/.env.example   # остаётся в контексте
   configs/.env.local     # исключён
   ```

4. Собрать образ или проверить контекст по пункту «Проверка».

## Эталон

Готовый файл — `references/.dockerignore`. Скопировать в корень проекта и
дополнить под проект.
