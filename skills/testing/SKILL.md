# Тестирование Go-проекта

Навык отвечает на вопросы «**что тестировать unit-тестами**», «**чем**» и
«**как оформлять тест**». Интеграционные тесты — `skills/integration-testing`;
e2e — `skills/e2e-testing`. Вопрос «где лежит файл» — в
`skills/project-structure`; «какие зависимости допустимы» — в
`skills/architecture`; «как устроен конфиг» — в `skills/config`; «как устроен
сервис» — в `skills/services`; «как устроен транспорт» — в
`skills/transport`.

## Принципы

1. Тест проверяет **поведение**, а не реализацию. Если рефакторинг без
   изменения поведения ломает тест — тест был про внутренности.
2. **Один тест — одно поведение.** Кейсы одного поведения — строки таблицы,
   а не разные тесты.
3. Тест **детерминирован**: фиксированное время, сид, порядок, изоляция.
4. Unit-тест **быстрый и без I/O**: без сети, диска, БД и брокеров.
5. Тесты **независимы**: ни один не зависит от порядка запуска и данных
   другого.
6. Тест **читается как документация**: имя описывает ситуацию, сообщение при
   падении объясняет, что не так.
7. **Новое поведение — с тестом.** Баг — сначала тест, воспроизводящий баг,
   потом исправление.
8. Если код трудно тестировать — это сигнал о границах, а не повод добавить
   тестовый флаг в прод-код.

Из принципа 1 есть исключение — **чистые приватные функции** (парсеры,
нормализаторы, мапперы без I/O и состояния) и **тестовые швы** — приватные
функции с подменяемой зависимостью, например writer. Для чистой функции
сигнатура и есть контракт: тест можно писать напрямую, а при переименовании —
обновить вместе с функцией. Это дешевле и точнее, чем гонять каждое значение
через публичный API. Запрет ниже — про приватные методы, которые дублируют
публичное поведение.

## Уровни тестов

| Уровень | Навык | Кто пишет |
|---|---|---|
| Unit | `skills/testing` | разработчик |
| Интеграционные | `skills/integration-testing` | разработчик, по согласованию |
| E2E | `skills/e2e-testing` | тестировщик, разработчик помогает |

Основа — unit: быстрые, без I/O и внешних сервисов. Интеграционные и e2e
добавляются отдельно и не дублируют unit.

## Стек по умолчанию

- **`testing` из stdlib** + table-driven тесты.
- **`testify`** — по умолчанию: `require` для проверок, без ручных `if`.
  Отказ — только по явному запросу пользователя.
- **`mockery` v3** — по умолчанию для моков интерфейсов; `minimock` — если
  проект выбрал его. Конфиг — `.mockery.yaml` в корне, версия — в `Makefile`
  (`MOCKERY_VERSION`). Моки генерируются, руками не пишутся.
- **`httptest`** для HTTP, **`bufconn`** для gRPC, обычные каналы и фейки для
  остального.
- **Фейки руками** — только если пользователь явно отказался от генератора
  моков.
- **Testify и mockery — стандарт репозитория.** Не заменять их на ручные
  `if` и самописные моки ради «нуля зависимостей»: тестов будет много, а
  конфиг пишется один раз.

Если проект уже принял другой стек — следовать проекту. Навык задаёт
поведение по умолчанию, а не запрещает осознанные отклонения.

## Что тестировать unit-тестами

| Слой | Что проверяем | Где |
|---|---|---|
| `domain` | инварианты, границы значений, ошибки | `internal/domain/..._test.go` |
| `services/<appname>/<service>` | операции, оркестрация, ошибки, идемпотентность на фейках | `internal/services/<appname>/<service>/..._test.go` |
| `transport/<appname>` | разбор запроса, маппинг ошибок, коды; `httptest`/`bufconn`, фейковые операции | `internal/transport/..._test.go` |
| `platform/<pkg>` | парсинг, настройка, дефолты | `internal/platform/..._test.go` |
| `config` | парсинг env/файла, дефолты, перетирание env файлом | `internal/config/..._test.go` |
| `infra/<adapter>` | валидация `Config` в `New`, маппинг без реальной системы | `internal/infra/<adapter>/..._test.go` |

Не unit-тесты:

- реальные БД, брокеры, сеть и миграции — `skills/integration-testing`;
- полный пользовательский сценарий через приложение — `skills/e2e-testing`;
- контракт репозитория с реальной БД — `skills/integration-testing`.

## Unit-тесты

### Расположение и имена

- Файл — рядом с кодом: `order.go` → `order_test.go`.
- По умолчанию пакет тот же (`package order`), чтобы тестировать поведение
  без экспорта лишнего. `package order_test` — когда проверяется только
  публичный контракт.
- Имя теста — `TestOrder_Validate`, `TestCreateOrder_RejectsZeroAmount`.
  Подтесты — короткие фразы: `t.Run("zero amount", ...)`.
- Имена тестов и подтестов — на английском, как и код.

### Table-driven

```go
func TestOrder_Validate(t *testing.T) {
	t.Parallel()

	tests := []struct {
		name    string
		amount  int
		wantErr error
	}{
		{name: "positive amount", amount: 100},
		{name: "zero amount", amount: 0, wantErr: domain.ErrInvalidAmount},
		{name: "negative amount", amount: -1, wantErr: domain.ErrInvalidAmount},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			t.Parallel()

			order := domain.Order{Amount: tt.amount}
			err := order.Validate()

			if !errors.Is(err, tt.wantErr) {
				t.Fatalf("Validate() error = %v, want %v", err, tt.wantErr)
			}
		})
	}
}
```

Правила таблицы:

- Колонка `name` — обязательна и описывает ситуацию, а не номер кейса.
- Ожидаемая ошибка — sentinel или тип, проверка через `errors.Is` /
  `errors.As`. Сравнение строк ошибок запрещено.
- `t.Fatalf` — когда продолжать бессмысленно; `t.Errorf` — когда проверок
  несколько и нужны все результаты.
- В сообщении — фактическое и ожидаемое значение: `got %v, want %v`.

### Детерминизм

- Время — через порт `Clock`, а не `time.Now()` внутри логики. В тесте —
  фиксированное время.
- Случайность и ID — через порт `IDGenerator` или сид. В тесте — предсказуемая
  последовательность.
- Порядок map/срезов — сортировать перед сравнением.
- `time.Sleep` для синхронизации запрещён. Нужно ожидание — polling с
  дедлайном (`t.Deadline`, `context.WithTimeout`) или канал.

### Параллельность и хелперы

- `t.Parallel()` — в независимых тестах и подтестах. Общее изменяемое
  состояние при этом недопустимо.
- Хелперы помечать `t.Helper()`, чтобы в отчёте была строка вызова.
- Освобождение ресурсов — `t.Cleanup()`, а не отложенный `defer` в вызывающем
  тесте.
- `t.Fatal`/`require` нельзя вызывать из горутины: только `t.Error` и возврат
  ошибки.

## Фейки и моки

Фейк — ручная реализация порта с нужным тесту поведением. Это резервный
вариант: по умолчанию в каркасе `mockery` v3 + `testify`, и моки на интерфейсы
генерируются, а не пишутся руками. Фейк остаётся для сценариев, где нужно
состояние, а не проверка вызовов.

Если пользователь явно отказался от генератора моков — фейки пишутся руками.
Генератор ставится через `.bin-deps`.

```go
type fakeOrderRepository struct {
	saved []domain.Order
	err   error
}

func (f *fakeOrderRepository) Save(_ context.Context, o domain.Order) error {
	if f.err != nil {
		return f.err
	}
	f.saved = append(f.saved, o)
	return nil
}

var _ repository.OrderRepository = (*fakeOrderRepository)(nil)
```

Правила:

- Фейк реализует **порт**, а не конкретный адаптер.
- Фейк живёт в `_test.go` пакета-потребителя. Если он нужен нескольким
  пакетам — в `internal/testkit/`. Прод-код `testkit` не импортирует.
- Домен и stdlib не мокаются. Внешние системы подменяются на границе порта.
- Проверяется результат и состояние, а не последовательность вызовов, если
  порядок не является частью контракта.
- Контракт порта проверяется общим набором тестов, который прогоняется для
  каждой реализации (фейк, БД, in-memory). Для фейка это unit, для реальной
  БД — `skills/integration-testing`.

## Покрытие

```bash
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

Ориентиры, а не gate:

| Слой | Ориентир | Что важнее цифры |
|---|---|---|
| `domain` | 80–90% | все инварианты и границы |
| `services` | 80% | комбинации правил |
| `transport` | не gate | маппинг и коды ошибок |
| `platform`/`config` | 80% | парсинг и валидация |

- Общий порог в CI по умолчанию не ставится: он провоцирует тесты ради цифры.
- Покрытие — метрика unit-тестов для поиска дыр, а не цель. Интеграционные и
  e2e дают уверенность, но не заменяют unit.
- Не тестируются: сгенерированный код, сторонние библиотеки, тривиальные
  геттеры, константы.

## CI и Makefile

```bash
go vet ./...
go test -race -shuffle=on -count=1 ./...
```

- `-race` обязателен: гонки не ловятся обычным прогоном.
- `-shuffle=on` выявляет зависимость от порядка.
- `-count=1` отключает кеш в CI.
- Интеграционные и e2e-тесты в этот прогон не входят: у них свои теги, цели и
  навыки.

Если в проекте есть `Makefile`, цели unit-тестов называются так:

```make
test:
	go test ./...

test-race:
	go test -race -shuffle=on -count=1 ./...

cover:
	go test -coverprofile=coverage.out ./...
	go tool cover -func=coverage.out
```

Цели `test-integration` и `test-e2e` — в `skills/integration-testing` и
`skills/e2e-testing`. `AGENTS.md` ссылается на эти цели, а не придумывает
свои команды.

## Чего не делать

- Спать в тесте и надеяться, что успеет.
- Держать общее изменяемое состояние между тестами.
- Ходить в реальную сеть из unit-теста.
- Терпеть нестабильный unit-тест (flaky) и перезапускать его до зелёного: он
  чинится или удаляется.
- Проверять текст логов вместо поведения.
- Мокать домен, stdlib и то, чем не владеешь.
- Писать моки руками, когда в каркасе есть `mockery` или `minimock` (по
  умолчанию).
- Вызывать `t.Fatal`/`require` из горутины.
- Игнорировать ошибку: `_ = fn()` без проверки.
- Использовать `panic`/`os.Exit` в тесте.
- Писать один огромный тест на весь сценарий.
- Писать тест только ради покрытия.
- Тестировать приватные методы, которые дублируют публичное поведение, в
  обход контракта.
- Забывать про `-race` и `-shuffle`.

## Когда тест обязателен

- Новое поведение или новая ветка логики.
- Исправление бага — regression-тест.
- Изменение контракта порта или API.
- Изменение формата данных и сериализации — unit; SQL и миграции — unit на
  маппинг плюс integration (`skills/integration-testing`).

Не обязателен:

- Чистый bootstrap в `cmd`, если он покрыт smoke/e2e.
- DI в `app.go`, если он покрыт smoke/e2e.
- Сгенерированный код.
- Документация и конфиги без логики.

## Ревью-чеклист

1. Имя теста описывает поведение, а не метод?
2. Проверен ли не только happy path, но и ошибки/границы?
3. Тест детерминирован: время, сид, порядок, изоляция?
4. Нет ли I/O в unit-тесте?
5. Данные изолированы, есть ли `t.Cleanup`?
6. Проверяется контракт, а не внутренности (кроме чистых приватных функций)?
7. Сообщение при падении объясняет `got`/`want`?
8. Нет ли дубля с другим тестом?
9. Проходят ли `-race` и `-shuffle=on`?
