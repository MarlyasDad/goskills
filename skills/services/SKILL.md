# Сервисы приложения

Навык отвечает на вопросы «**как проектировать сервис**», «**где его код**» и
«**как он оркестрирует**». Какие импорты допустимы — в
`skills/architecture`; физическая раскладка — в `skills/project-structure`;
тесты — в `skills/testing`.

## Термины

- **Use case** — один сценарий: `OnboardingUser`, `RemoveUser`.
- **Сервис приложения** — реализация use case: каталог, структура и `New`.
  Один сервис может реализовывать несколько use cases.
- **Доменный сервис** — правило над несколькими агрегатами, без оркестрации
  и I/O.
- **Сага** — координатор распределённого процесса с компенсациями. Не слой и
  не замена сервису.

## Каталог

Один каталог на сервис:

```schema
internal/services/<appname>/<service>/
├── ports.go        # интерфейсы зависимостей
├── service.go      # struct Service + New
├── dto.go          # Input / Output
├── register.go     # один use case
├── unregister.go   # другой use case
└── register_test.go
```

`<service>` — короткое имя по смыслу: `user`, `subscription`, `report`.
Не складывать все сервисы приложения в один пакет.

## Файлы

### ports.go

- Интерфейсы, которые нужны **этому** сервису: репозитории, часы, внешние
  порты.
- Не дублировать общие порты из `repository`/`shared`.
- Входящие интерфейсы объявляет потребитель: `transport` — для операций,
  которые вызывает.

### service.go

```go
package user

type Service struct {
	users         UserRepository
	subscriptions SubscriptionRepository
	clock         Clock
}

func New(users UserRepository, subscriptions SubscriptionRepository, clock Clock) *Service {
	return &Service{users: users, subscriptions: subscriptions, clock: clock}
}
```

- Зависимости — интерфейсы, не конкретные адаптеры.
- `New` не создаёт клиентов и не читает env.

### dto.go

- `Input`/`Output` для методов: `RegisterInput`, `RegisterOutput`.
- `Request`/`Response` остаются на транспорте.
- Не протаскивать ORM-модели и HTTP-теги.
- Если проект выбрал другую пару (`Request`/`Response`) — придерживаться её
  во всём модуле.

### <method>.go

- Один публичный метод — один use case — один файл: `register.go`,
  `unregister.go`.
- Тест рядом: `register_test.go`.
- Вспомогательные функции — в том же файле или в `service.go`, если общие.

## Правила

- Сервис группирует **родственные** use cases. `OnboardingUser` и
  `RemoveUser` — два use case одного `UserService`.
- Один метод — нормально, если это полный сценарий.
- Не заводить отдельный пакет или слой под use case: его реализует метод
  сервиса.
- Сервис оркестрирует домен, репозитории и транзакции, но не содержит
  бизнес-правил, которые принадлежат сущности или доменному сервису.
- Не знает про HTTP-коды, SQL, Kafka-топики и конкретные адаптеры.
- Внешние эффекты — через порты из `ports.go`.
- Ошибки оборачивать с контекстом: `fmt.Errorf("register user: %w", err)`.

## Оркестрация

- Порядок шагов, транзакция и идемпотентность — в сервисе.
- Если операция затрагивает несколько агрегатов в одной БД — одна транзакция
  в сервисе.
- Если несколько сервисов/БД/внешних систем — сага, а не ручной набор
  компенсаций в сервисе.

## Сага

- Сага — координатор распределённого процесса: шаги и компенсации.
- Для одной транзакции в одной БД не нужна.
- Живёт в application-слое:
  - одна-две — файл `services/<appname>/saga_register.go`;
  - много — подпакет `services/<appname>/sagas/`.
- Два входа:
  - сервис-фасад вызывает сагу;
  - сага сама является use case, transport вызывает её через интерфейс.
- `app.go` собирает сагу с адаптерами и сервисами.
- Не делать два оркестратора: сервис и сага не должны дублировать шаги.
- Сага не в `infra` и не в `transport`.

## Тесты

- Unit на каждый метод: успех, ошибка репозитория, граничные случаи.
- Зависимости — фейки или сгенерированные моки; без реальной БД и HTTP.
- Транзакция и идемпотентность проверяются на фейках.
- Подробно — в `skills/testing`.

## Антипаттерны

- Один `Service` на всё приложение.
- Сервис на каждый метод без причины.
- SQL, HTTP и JSON-теги в сервисе.
- Бизнес-правила в сервисе вместо `domain`/доменного сервиса.
- `Request`/`Response` в сервисе вместо `Input`/`Output`.
- Сервис вызывает `app` или `transport`.
- Сага внутри обычного сервиса как набор `if`/`switch`.
- Два оркестратора: сервис и сага.
