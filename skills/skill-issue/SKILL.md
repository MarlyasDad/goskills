# Issue по навыкам

Навык отвечает на вопрос «**как сообщить о проблеме в goskills**». Правка
навыков — `skills/skill-creator`; проектные отклонения — `skills/agents-md`.

## Когда заводить

- Два навыка требуют разного для одного случая.
- Навык противоречит своему `references/` или примеру в тексте.
- Команда, путь или пример не работают.
- Правило устарело после изменения репозитория.
- Есть предложение, которое снимает повторяющуюся путаницу.

Не заводить issue, если:

- агент неверно прочитал навык — это ошибка агента, её нужно исправить в
  работе;
- правило не подходит проекту, но не противоречит навыкам — это отклонение
  проекта, его фиксируют в `AGENTS.md` после согласования;
- вопрос уже описан в другом навыке — сначала прочитать его целиком.

## Проверка перед issue

1. Перечитай оба правила целиком, а не фрагмент.
2. Найди точные файлы и строки: `skills/<id>/SKILL.md:NN`.
3. Проверь, нет ли исключения в третьем навыке или в `references/`.
4. Отдели конфликт навыков от ошибки агента и отклонения проекта.
5. Воспроизведи команду или пример, если это возможно.
6. Если проблема не воспроизводится — не отправляй, сначала уточни.
7. Если `gh` доступен, проверь, нет ли уже открытого issue:

   ```bash
   gh issue list --repo MarlyasDad/goskills --search '<кратко>'
   ```

## Что собрать

| Поле | Что писать |
|---|---|
| Тип | `conflict`, `bug`, `docs`, `proposal` |
| Критичность | `blocker`, `major`, `minor` |
| Где | файлы и строки |
| Цитаты | короткие дословные фрагменты правил |
| Ожидаемое | как должно быть по смыслу |
| Фактическое | что происходит сейчас |
| Воспроизведение | минимальная команда или пример |
| Окружение | commit, дата, Go/OS, если важно |
| Предложение | какое правило главное и что поправить |

Критичность:

- `blocker` — правило невозможно выполнить или команда ломает проект;
- `major` — навыки требуют разного, нужно выбирать;
- `minor` — опечатка, неточность, устаревший пример.

## Текст issue

Заголовок: `[skills] <кратко>` или `skills/<id>: <кратко>`.

````markdown
## Что случилось

<одна-две фразы>

## Тип и критичность

conflict / major

## Где

- `skills/<a>/SKILL.md:NN` — <что требует>
- `skills/<b>/SKILL.md:NN` — <что требует>

## Ожидаемое

<как должно быть>

## Фактическое

<что происходит>

## Воспроизведение

Выполнить: `<команда>`.

## Предложение

<какое правило считать главным, что поправить>

## Окружение

- goskills: <commit>
- дата: <YYYY-MM-DD>
- Go: <версия, если важно>
````

Пример из практики (уже исправлено): `skills/architecture` запрещал
`config → platform`, а `skills/logger` требует `Logger logger.Config` в
`internal/config`.

- заголовок: `[skills] config → platform: матрица запрещает, logger требует`;
- тип и критичность: `conflict`, `major`;
- предложение: разрешить `config → platform/<pkg>` только ради `Config`.

## Отправка

1. Покажи готовый текст пользователю целиком.
2. Спроси: «Отправить issue в `MarlyasDad/goskills`? Да / нет».
3. Отправляй только после явного «да».
4. Если есть `gh` и авторизация:

   ```bash
   gh issue create --repo MarlyasDad/goskills \
     --title "[skills] <кратко>" \
     --body-file <файл>
   ```

5. Если `gh` нет или нет сети — отдай текст и ссылку:
   <https://github.com/MarlyasDad/goskills/issues/new>.
6. Не отправляй секреты, внутренние адреса и код проекта; оставь только
   фрагменты навыков и минимальный пример.
7. В итоге дай номер issue и ссылку.
