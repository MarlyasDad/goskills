# Интеграционные тесты

Навык отвечает на вопрос «**что проверять с реальной инфраструктурой и как это
запускать**». Unit-тесты — `skills/testing`; e2e — `skills/e2e-testing`.

## Кто и когда

- **Пишет разработчик.** Он знает схему, SQL, брокер и контракт адаптера;
  тестировщик может помочь со сценариями, но не заменяет владельца кода.
- **Добавляются по согласованию.** Они поднимают инфраструктуру, стоят
  времени в CI и могут быть нестабильными. Не на каждый метод и не «для
  покрытия».
- Обязательны, когда меняется то, что нельзя проверить фейком:
  - SQL, миграции, индексы, транзакции;
  - сериализация и контракт внешней системы;
  - retry, timeout, идемпотентность на реальной инфраструктуре;
  - контракт репозитория или адаптера.
- Не нужны для чистой логики — это unit; для полного пользовательского
  сценария — это e2e.

## Тег и запуск

- Файл начинается с тега, затем пустая строка:

```go
//go:build integration

package integration_test
```

- Запуск: `go test -tags=integration -count=1 ./tests/integration/...`.
- Обычный `go test ./...` эти тесты не запускает.
- Цель в `Makefile`:

```make
test-integration:
	go test -tags=integration -count=1 ./tests/integration/...
```

- Файлы живут в `tests/integration/`; unit-тесты — рядом с кодом.

## Инфраструктура

- Выбирается одна: `testcontainers-go` или `docker-compose` проекта. Не
  тащить вторую инфраструктуру.
- Контейнеры и сервисы поднимаются в `TestMain` или общем хелпере, а не в
  каждом тесте.
- Миграции применяются тем же механизмом, что и в проде.
- Каждый тест изолирован: своя схема/база или уникальные ключи, очистка в
  `t.Cleanup`. Порядок тестов не влияет на результат.
- На всё внешнее — `context.WithTimeout`; тест без таймаута запрещён.
- Реальные production-сервисы, платные API и секреты не используются.
  Внешние HTTP/gRPC подменяются `httptest.Server` и `bufconn`.

## Контрактные наборы

- Для порта репозитория — общий набор проверок в
  `internal/testkit/repositorytest`.
- Один и тот же набор прогоняется для in-memory и реальной реализации.
- Набор проверяет контракт, а не детали SQL конкретной СУБД.
- Если реализация нарушает контракт, тест падает у реализации, а не у
  потребителя.

## Нестабильные тесты (flaky)

- Причина — общие данные, незафиксированный порядок, отсутствие таймаута,
  медленный контейнер.
- Нестабильный тест чинится или удаляется; ретраи — только для внешней
  инфраструктуры и с ограниченным числом попыток.
- Логи контейнеров и приложения сохраняются при падении.
